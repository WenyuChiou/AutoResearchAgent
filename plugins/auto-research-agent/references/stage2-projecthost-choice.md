# ProjectHost: Stage 1 import to a recorded Stage 2 choice

The trusted server imports a hash-pinned Stage 1 handoff and preserves its original
project ID, exact input-version type/value and confirmed brief. Browser submissions
contain an opaque project reference and the displayed version, never source paths,
model policies or execution settings.

For structured scientific candidates, bootstrap explicitly sets
`policy_ref.packet_profile=scientific-v3` before activation. The empty seed is
validated through the existing opt-in transitions before workflow initialization.
Legacy initialization stays unchanged. Existing workflow schemas are never replaced.
The profile descriptor binds the original packet, transition sequence and initial
scientific packet; reopening recomputes those bindings.

The project page links to direction comparison. A researcher can read each
question, methods, resources, limitations and unknowns; choose an eligible current
version; retain conditions and unresolved questions; and confirm the original UI
message. The server records its true ProjectHost origin and principal. It does not
claim that a user-entered name establishes native Codex or legal identity.

A saved choice composes the existing interaction and planning-handoff APIs and the
strict Stage 3 inspector. Reusing the same key reopens the saved artifacts, then
reconciles only the durable ProjectHost frontier. Unknown core outcomes stay held;
a new key cannot bypass them. The metadata request preserves the HTTP deadline and
revalidates activation/source inputs; operation-local values are not a cache for a
later request. Durable journal/CAS and artifacts are reopened after registration.

Historical HostReplay receipts retain their original validator/runtime bindings.
Changed validator bytes reject; neither this entry nor a replay invents replacement
source admission or alters an old failure. A new currently bound verification is
required where applicable.

Zero recommendations remain a readable decision package. They are not selectable
and cannot become a selected Stage 3 plan. A successful planning-input inspection
still leaves `execution_authorized=false`. Native research preparation, complete
controller admission, real human selection and research execution remain separate
states; UI success does not stand in for any of them.
