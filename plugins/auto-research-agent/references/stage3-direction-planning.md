# Conditional direction input

The Stage 3 consumer accepts a pinned Stage2DirectionPlanningIntent and the
existing verified advisory package. The trusted Host must separately verify the
current project, receipt, source frontier and candidate versions; artifact
consistency cannot authenticate a person or make a formal selection.

The context retains preferred candidates, original SQs, assessments, evidence,
resource constraints, source-global unknowns, pending scope questions and user
conditions/unknowns separately. selected_options stays empty,
human_selection stays pending and execution_authorized stays false. Missing
source SQs cannot be filled by the consumer.

The generic prompt retains every original value. A sole $ key references an
integer index in a shared table; $literal escapes source objects with reserved keys.
Expansion must reproduce the original context hash. The existing 48,000-byte
context limit is unchanged; oversized or unmapped contexts need clarification.
DirectionPlanningJobs wraps the existing planning journal and single-dispatch
state machine, finite positive adapter deadline and existing request-size bound.
Project, method and original key identify separate output directories.
Preparation, inspection and replay invoke no callback; explicit
run uses the configured callback once. Failed raw output and provenance remain
saved; uncertain attempts use the existing explicit reconciliation rules.

Stage3DirectionPlanningResult retains one row for each original question_ref,
including materials, method, design, validation, analysis, interpretation,
unknowns and minimum deliverable. It is a conditional draft, not a selected plan,
scientific acceptance or evaluation subject. Host/UI integration and real native
planning remain unverified.

The Host adds mode=direction-intent to the existing planning API. Its key is
stage3-direction- plus the saved intent hash; current project/source bindings
are checked before dispatch and publication. Read, prepare, inspect and recover
never call the planner. Missing source questions or an oversized context return
needs-information, visible planning_blockers and no default_request. The saved
preference is retained. An identical complete input left before journal creation
is reused; a mismatched or partial input remains an explicit failure.

The API retains the original per-question materials and conditional result for
the Wiki presentation slice. Saved jobs must still match the current Host model,
adapter and source bindings; recovery availability uses the existing trusted pin
map. Source unknowns and user conditions remain separate. The target is a Stage 3
planning job; agent_conversation_connected=false. Deployment, Wiki integration
and native/scientific acceptance remain separate; execution_authorized=false.

The Wiki presentation joins each original question to its own recorded materials
and conditional method, design, validation, analysis and result interpretation.
It separates source unknowns, user conditions and missing mappings. Common
resource fields have plain labels; nested original details remain expandable.
Three-language copy keeps direction preferences and conditional drafts distinct
from formal selections. Reading or changing language dispatches nothing; explicit
actions reuse the saved typed request and key. Original raw values remain in the
receipt view. Deployed/native/scientific and whole-flow acceptance remain unverified.

Recorded next-check objects show their original text, with source markers and
other recorded fields available in expandable details. Rendering changes no values.

The planning entry shows the original direction or source questions, the current
recorded state and one primary next action. Running and saved jobs do not show
another start form. A saved draft marked needs-information stays visibly
conditional; missing information is not inferred to be resolved. The main view
prioritizes per-SQ design and outstanding conditions; versions, authority and raw
receipts are expandable. An explicitly accepted run is followed by a passive
read of the actual job. Opening, refreshing or changing language never dispatches.
Loading, read failures and uncertain outcomes retain a safe read/inspect path.
Verified current job outcomes take precedence over retained connection errors.
A connection error affects current controls only when its key and request hash
match; all historical errors remain unchanged in the raw receipt.
When an explicit action hides its old control, keyboard focus moves to the
applicable confirmation, draft-review or read-state control on the same project.
Before a plan exists, headings identify original questions and source conditions.
Entry uses the canonical HTML path and #encoded-project?lang=en|zh-TW|zh-CN;
the fragment is client-only, so the strict Host route needs no query support.
Unknown or malformed project fragments select no project and read no other one.
Explicit project/language changes replace the current permalink without storage
or an extra planning call. Review buttons scroll/focus without replacing the
project fragment, so reloading retains the same project and language.
Three-language, narrow-screen and keyboard checks establish presentation behavior
only; usability with researchers and scientific acceptance remain unverified.

## Supplemental evidence and design-review primitives

The optional DirectionResearchAdapter pairs separate Host-configured planning and
review callbacks. prepare_direction_evidence performs at most one trusted lookup
per named gap; the planner receives only hash-bound evidence and source locators.
Source status and limitations remain explicit; receipt integrity is not proof of
scientific support, data rights or usable access. No lookup service reaches a model.
research_context preserves every original question, source condition and unknown.
The source-design-v1 profile is explicit and rejects unknown profiles.
The independent review prompt includes the entire delivered plan, its overview,
original conditions and separately labelled prior assessment advice. It asks whether
the first comparison is feasible and whether a fallback still answers the question.
Review results bind the exact plan, intent and every original question reference.
This slice prepares and validates these inputs only. Automatic durable job/native
review wiring, plan revision, deployed acceptance and scientific quality remain
separate verification steps; no execution authority is added.

## Durable optional design review

DirectionPlanningJobs uses the existing journal and immutable package for the
explicit source-design-v1 profile. A configured independent review callback is
required before planning dispatch. Each callback retains its own native capture;
the review uses the dedicated stage3.direction-design-review.v1 operation with
the configured model, tools and finite deadline unchanged.

The package seals the full delivered plan, review prompt/schema, raw response and
review record. Unknown or needs-revision answers retain a saved needs-information
result. A reviewer failure retains the completed plan and all written review
bytes; same-key replay inspects those hashes and never retries either callback.
Completed read-only inspection preserves the historical request binding. Jobs
without this explicit profile keep the original prompt and single planning call.
These checks establish recovery and traceability only. The caller still owns
source admission, configured services and any explicit new revision; no automatic
revision, scientific acceptance or research execution authority is introduced.

## Registered-material preparation API

A trusted caller can explicitly call prepare_registered_materials with an authenticated
catalog, full-file reader and selected JSON pointers. inspect_registered_materials
recomputes the saved projection from its externally pinned original files. The
existing artifact and context bounds remain in force. Consumer project, typed
input version, intent and delivery identity are bound separately from catalog
metadata. Keep unreviewed status, access limitations and unknown rights visible.
Matching partial preparation reuses saved reads; completed replay performs no read.
This API prepares inputs only. Planner, independent-review and Host forwarding
require their separate integration; no model dispatch or research authority is added.

## Typed study-route projection API

The separate structured-direction schema requires four proposed phases: baseline,
prototype, independent verification and qualified continuation. Each phase names
its inputs, procedure, output, decision, blocked branch and timebox. Response
questions retain explicit acquisition, pairing, identification, development lock,
pre-reveal prediction, independent reveal, scope and blocked-case steps.
project_study_route validates this raw value and derives the existing public
method text, while retaining source unknowns and false execution authority.
This schema/projection API does not enable a job/profile or dispatch a model.
The original raw value is unchanged; durable sealing and Host integration are separate.
