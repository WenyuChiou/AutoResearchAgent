# Read-only research workspace

This first #80/#82 slice projects an existing Stage 1 package into an English
HTML workspace, notes, a graph, a complete catalog and bibliography. It does not
change canonical research records or rebuild the original deliverable. English
is the first-load UI language; simplified and traditional Chinese remain available.
Source titles, authors, claims, quotations and reasons retain their original text.

`project_package` requires an externally supplied SHA256 for the outer
`package_manifest.json`. It checks file inventory and bytes, the inner manifest,
record identities and source/claim bindings before projecting them. The default
`byte-inventory` projection explicitly does not attest original runtime replay.
Full semantic replay belongs to the existing deliverable validator in its pinned
runtime and is outside this read-only adapter. Failed replay stays failed; the
adapter cannot substitute byte checks for that result. Projection establishes no
scientific sufficiency, independent evaluation or execution authority.

The view reuses the four reference assets from #88 at exact head
`085f363179a79375fc8e3590dda9725e25eda71a`. Supply that checkout's
`plugins/auto-research-agent/references/research-workspace` as `--reference-root`.
Asset hashes are checked and bound to the output receipt. This is an explicit
Draft reference dependency; core acceptance of replacement coverage and native
execution remain separate gates.

Set `PYTHONPATH` to the plugin's `cli` directory and run:

```text
python -B -X utf8 -m research_workspace PACKAGE_ROOT NEW_OUTPUT_DIR \
  --project-id PROJECT_ID \
  --expected-manifest-sha256 OUTER_MANIFEST_SHA256 \
  --reference-root PINNED_REFERENCE_DIRECTORY
```

Use a new output directory outside Git for each snapshot. Open its `index.html`
in a browser; it reads the saved index without fetching papers or making model
calls. The `wiki` directory also preserves readable Markdown notes. Notes and graph edges retain exact work/version identity, field provenance
and input bindings. BibTeX selection only joins entries generated by the existing
canonical producer. Filtering cannot silently redefine the all-record export.

All six stages remain navigable. Execution controls stay disabled, including
Stage 2: displaying review-only evidence cannot approve its import or start.
Missing metadata, unavailable source content, partial/unverified claims and open
coverage remain explicit. An absent supplement means Top 3 is pending, not that
three findings have been synthesized. Roles do not imply citations or shared
methods; classification tags without supplied concept IDs remain unmapped.

This slice does not implement persistent sessions, pending native answers,
scoring, selected reruns or two-topic native Windows acceptance. The accepted
core APIs are reused in subsequent slices. New search intake, scoped browser
consent, live permissions and budgets must pass their existing gates. No frozen
package, rubric, baseline result, attempt or old Draft is changed by rebuilding.

Run deterministic regressions with the repository's pinned test environment:

```text
python -B -X utf8 -m unittest discover -s plugins/auto-research-agent/tests -p "test_research_workspace*.py" -v
```

Private papers, source text, actual indexes and snapshots never belong in Git.
Public fixtures are synthetic. Rendering success and byte checks do not prove
P1-P3 quality improvement or actual native execution.

### Separately bound PDF body review

A saved-source rerun may reference an engineering-only body-review bundle and
its canonical verification result. Supply each externally accepted digest with
`--expected-body-review-acceptance-sha256`; a declared digest inside the bundle
alone is insufficient. The adapter verifies source, version, reading attempt,
original parser, independent reader/runtime artifacts, every page, quotations,
and separately reviewed discrepancies before attaching evidence.

The verification result must also be a byte-bound rerun artifact. Its cached
projection is checked again against that artifact and the current reading.
The original source rows, automatic diagnostics and body-completeness decision
remain unchanged. Evidence appears separately in selection bindings and saved
rerun exports; this slice cannot grant formal eligibility, authenticate declared
reviewer identity, repair scientific claims or authorize Stage 2 execution.

### Accepted private repair overlay API

`project_package` accepts `repair_root`, `expected_repair_manifest_sha256` and
`expected_repair_review_sha256` together. External hashes bind the private
candidate manifest and independent delta review. Every listed member and exact
source passage is checked before a copied WorkspaceIndex v2 is returned. The
unchanged v1 schema and default projection remain supported.

The overlay retains original claims, compound judgments, unknown coverage,
failed attempts and the original rejected review. Atomic revisions and core
findings keep separate denominators and typed provenance. Recovered abstract
content does not establish full-method access; presentation grants no Stage 2
import, execution or scientific-quality upgrade.

The CLI accepts the same three optional repair arguments and emits English
HTML, version-bound notes, a complete bibliography and editable Excel/CSV.
`closeout/` contains the accepted atomic mapping, core findings, input/runtime
bindings and Traditional Chinese status summary. `repair/` retains the checked
acceptance and source-evidence snapshots. All outputs remain outside Git.
Opening, exporting or rebuilding this view performs no research or scoring.

Saved-source reading is an explicit offline API: `source_rerun.build_rerun` accepts an original v1/v2 index, saved-source root, new private output and exact local parser hash. It preserves source bytes and historical attempts, records new extraction/access failures, and binds runtime versions. It performs no acquisition or judgment. This reader slice does not activate v3 attachment, UI or formal Stage 2 import.

`source_rerun.attach_rerun` accepts that private manifest only with an external
SHA-256. It verifies the complete artifact inventory, saved response and
extracted-text bytes, parser-bound attempt IDs, work/source/version identities,
locators and metadata provenance before returning WorkspaceIndex v3. Original
claims, coverage, Unknowns, failures and source receipts remain unchanged.
Abstract extraction cannot become full text, and the overlay cannot authorize
research, new acquisition, scientific judgment changes or Stage 2 import.

The CLI accepts `--source-rerun-root` with its external manifest SHA-256 and
emits the v3 overlay as read-only HTML, per-work Wiki notes, Excel/CSV,
Markdown and BibTeX. Every exported source byte remains private and bound to
the accepted manifest. Rebuilding a saved v3 view reads only those artifacts;
it does not rerun the parser, acquire sources, score quality or alter the
original scientific record.

The derived `literature_selection` payload applies one topic-independent rule:
include readable full text with matching work/source/version/hash and confirmed
source identity. Abstract-only, metadata-only, inaccessible, failed, truncated
or explicitly incomplete sources remain in the screening list with their reasons.
Readable full text whose identity is unverified stays pending. A claim's Unknown
status does not remove an otherwise eligible work. Legacy indexes without a
current source review stay pending; no historical record is rewritten.

Selection rule `1.1.0` also requires affirmative body-extent evidence. PDF
receipts reconcile the total, readable and located pages and extracted-text
extent. Non-PDF receipts require a full-body `document_extent` bound to the raw
and extracted hashes, matching character counts and a complete body locator.
A `full-text` label or `complete: true` alone is insufficient. Missing proof or
unreviewed extraction fidelity stays pending; contradictory extent is excluded.
These checks establish recorded extraction extent, not semantic correctness,
claim support or research sufficiency. Old source records are never restamped.

`literature/` exports the same bound selection as JSON, CSV, Markdown, Excel
(Included, Screening and Selection sheets), an included bibliography and the
complete screening bibliography. The payload provides the frontend contract;
new selection bibliographies use version-bound citation keys recorded in each
selection row; the original complete bibliography retains its existing keys.
New rerun manifests can opt into `citation_key_policy: work-version-sha256`
for the complete bibliography too. Unknown policies fail closed; absent policy
preserves historical manifests without rewriting their keys.
it does not attest the separately required visual/native acceptance. Coverage,
scientific assessments, full-record exports and official Stage 2 eligibility
remain unchanged. Rebuilding these exports performs no new research or reading.

### Separate recorded academic screening

`academic_screening.derive_academic_screening(index)` and
`academic_screening.academic_screening_files(index)` implement the additive
`S1-SCREENING-READMODEL-1.0.0` contract. Use
`selection_files(index, include_academic_screening=True)` to add these sidecars;
the default six selection files, technical statuses/reasons/eligibility, existing
catalog sheets, claims and HTTP interfaces retain their previous behavior.
The new `literature/academic_screening.json`, `.csv`, `.md`, `.xlsx` and
`academic_screening_history.csv` preserve recorded include/exclude/pending reasons.
The independent workbook contains AcademicScreening and ScreeningHistory sheets.
History uses one event per row; oversized individual Excel cells reference the
complete JSON field by pointer and SHA-256. JSON/CSV keep complete original values.

Counts describe only this index's paper/version rows; the historical candidate
total remains Unknown. Canonical 1.2 uses the complete bound library history,
including unread candidates and not-screened rows. Its original decisions are
work-level and do not declare a version: current display versions and separately
bound current reviews never rewrite original events. Older records preserve their
saved order/reasons, but absent history and history completeness remain Unknown.
Original reasons may be shared development templates. `reason_shared_work_count`
counts distinct works sharing each exact nonempty current reason, while
`counts.distinct_current_reasons` counts distinct nonempty reasons. These counts
make reuse visible without judging it. Recorded/nonempty fields
do not establish scientific adequacy; `scientific_assessment=false`, source
qualification, claim Unknowns and Stage 2 authority remain independent.

### Final-delivery prerequisites and phase timing

The opt-in [current saved-source admission](../../references/stage1-saved-admission.md)
uses a distinct snapshot and handoff version with externally accepted Core and
actual HTML evidence. The prerequisite checker below and every legacy gate retain
their original meanings; a new blocked candidate grants no final acceptance.

A candidate checkpoint is part of Stage 1; it is not the finished researcher
delivery. The complete chain is confirmed intake → actual search/acquisition →
read/screen and verify identity/version → admit the formal set → file and
validate all editable reports → accept Stage 1-to-2 handoff → verify actual HTML
operation. Retain claim Unknowns and incomplete coverage through this chain.

`python -m research_workspace.final_delivery VIEW_ROOT
--expected-view-manifest-sha256 VIEW_HASH --brief BRIEF_PATH
--expected-brief-sha256 BRIEF_HASH` inspects only saved prerequisites. It checks
the physical view inventory, exact source-rerun bytes, derived selection, paper
notes, HTML data payload and screening bibliography. It recomputes the confirmed
formal-work target using distinct work IDs; two versions never count as two works.
A pending intake remains pending. Status is `partial` or `ready-for-final-checks`,
never completed. The report lists semantic deliverable validation, brief/input
lineage, coverage/claim review, accepted handoff and actual HTML acceptance as
separate required checks. It does not execute their validators or a browser.

Formal progress requires an explicit `fresh_note.source_qualification` with
exact work/version/source/raw/text bindings, affirmative identity/body/order/
relevance checks and evidence references. A paper's input version must match
the brief. Technical `included` counts and an authored admission label alone
do not qualify a work. Notes remain separately complete or pending; individual
Unknown claims do not exclude a qualified source. Every brief need must appear
in coverage before target-and-covered can stop quantity work.

Optional `--resources PATH --expected-resources-sha256 HASH` binds query and
acquisition receipts, each with integer `used` and `limit`. Saved review backlog
precedes new acquisition; parser/identity backlog gets a diagnostic decision.
Exhaustion with no backlog yields a partial result. These decisions authorize
no actions. If a view displays `readiness.formal_progress`, the checker requires
it to equal the same derived result.

The optional `--timing PATH --expected-timing-sha256 HASH` binds an immutable
`Stage1RunTiming` v1 record to the project, input version and canonical index hash.
Its fields are `started_at`, nullable `ended_at`, `observed_at` and `intervals`;
each interval has `id`, `phase`, offset timestamps and nonempty `evidence_refs`.
Phases: intake, search, acquisition, reading-screening, identity-version,
filing-export, handoff, html-acceptance, engineering, ci-wait. Overlapping
intervals are merged for active accounting. Engineering and CI are shown
separately; missing measurements stay null. Timestamps and evidence references
are operator-supplied observations, not authenticated execution proof. Run-end
time does not prove final acceptance. Candidate export time and time to CI
submission must not be presented as the complete Stage 1 duration.

The command emits a JSON report on stdout and writes nothing. Its runtime source
hashes are separate from the original package runtime and preserved replay
failures. Opening/checking a view grants no source access, import or execution
authority. Actual HTML acceptance must use separately admitted browser/service
evidence; static syntax or generated bytes are insufficient.

`normalized_page_comparison.compare_normalized_page_evidence` checks two supplied
page strings against recorded NFC/whitespace hashes, equality and ordered differences.
Punctuation, word boundaries and character order remain significant. This pure
helper performs no acquisition, reading, research or scoring. Its comparison facts
do not certify full-body coverage, identity, independent acceptance or eligibility.

## Per-work retrieval trace (delivery review 1.4)

The current `S1-DELIVERY-REVIEW-1.4.0` exports add
`academic_screening.json.rows[].retrieval_trace` in the JSON, CSV, Markdown and
Excel views. They preserve the index and all scientific decisions.
`first_discovery.round_number` comes from the earliest actual discovery in a
bound canonical 1.2 run, including its original version/query/attempt and time.
An unknown first round stays null even if a later discovery has a known round.
The four counts remain separate: discoveries, distinct queries,
discovery-producing backend attempts, and all attempts of those producing
queries. Work query history excludes queries that never returned the work;
these counts do not mean searches until first discovery.

For recovered legacy observations, `saved_observation_count`,
`distinct_saved_batch_count` and `first_saved_batch_by_inventory_order` describe
only the saved observation inventory. They do not establish research rounds,
API retries or chronological first discovery. Missing links use null, never zero.
Only valid include work/version mappings contribute; duplicate observations
follow the validated identical-URL chain to that include mapping. The trace
keeps separate pointers to the observation, its review and the resolved mapping.
Excluded/pending injected link fields cannot create discovery credit.

Consumers should display current review reasons and keep old records in audit
exports rather than a default legacy panel. Rationale folding and actual graph
keyboard acceptance belong to the independently versioned UI consumer.
Old delivery-review contracts 1.0 through 1.3 keep their exact formatter bytes
and remain accepted by the final prerequisite checker. New views always bind
the trace and exporter source hashes, including runs without recovery records.

### Pinned saved search ledger (optional)

An original-record recovery bundle may add `saved_search_ledger` to its
`recovery.json`. The opt-in specification is validated by
`SavedSearchLedger.v1.schema.json`; bundles without it retain their existing
projections and all four legacy formatter contracts. Every referenced original
file must be present in the recovery manifest with its exact SHA-256. Reuse the
existing `attach_original_records` API and new outside-Git output directory;
never edit an already frozen delivery.

```json
{
  "contract_version": "S1-SAVED-SEARCH-LEDGER-1.0.0",
  "input_version": "synthetic-input",
  "ledger": {"path": "run-control.json", "pointer": ""},
  "snapshot": {"path": "snapshot.json", "pointer": ""},
  "receipts": {
    "saved-batch": {
      "receipt": {"path": "saved-result.json", "pointer": ""},
      "query_parameters": {"path": "saved-result.json", "pointer": "/query"}
    }
  }
}
```

The original ledger and `SavedSourceCandidateSnapshot` must agree on the
project and input version. The snapshot's resources binding must match the
ledger bytes and SHA-256, and its deliverable binding must match the canonical
manifest already bound by the index. Each ledger reservation maps once to a
receipt with the original SHA-256; duplicate batches, omitted/extra mappings,
wrong observation receipt hashes or lengths, and mismatched inputs fail closed.
This establishes saved-byte binding, not trusted Core acceptance or Stage 2
admission. Original cumulative budgets, usage and other resource fields remain
in the attached original file; this projection does not change resource state.

`query_parameters` is optional. It can point to `/query`, `/queries` or
`/query_texts` in that batch's receipt, or to the exact ledger reservation's
`/search_reservations/<index>/query_texts`. An array contains strings or original
objects with a nonempty `q`/`query` field, including additional saved fields such
as `need`. Preserve these original objects. Its length must equal that batch's
reserved query count. Planned query IDs remain separately labeled. None of
these arrays maps a query or a backend attempt to an individual work.

The resulting additive attachment is
`original_record_recovery.payload.saved_search_ledger`. Its `batches` preserve
ledger pointers, source hashes, receipt bindings and distinct timestamps:
`reserved_at`, `started_at`, `receipt_persisted_at`, `tool_completion_time`, and
the separate receipt wrapper's `receipt_started_at`. Missing values stay null;
`not-separately-captured` remains explicit. Reservation or receipt persistence
times never become starts or per-work discovery times. A wrapper start does not
overwrite a missing ledger start. Known ledger timestamps must be timezone
aware and chronological within the batch.

Each already linked `academic_screening.json.rows[].retrieval_trace.observations[]`
adds a separate `batch_context` with the same projected batch. JSON, CSV,
Markdown and Excel carry it through the existing trace export. Original
observations, their hashes and screening reviews are byte-preserved. Per-work
`first_discovery`, actual rounds, backend counts and query attribution remain
unknown where the original evidence does not establish them. Batch parameters
are not searches until first discovery. New views and final prerequisite
checker receipts bind the optional producer module and schema hashes. Actual
UI adaptation, independent content acceptance and formal Stage 2 import remain
separate steps.
