# 工具清單的等待時間與未知狀態

真實 producer05 的 `plugin/list` 在 30 秒內沒有回覆，後面的 MCP 查詢成功。這證明該次 RPC 等待失敗；現有紀錄不足以分辨冷啟動或遠端取得問題。

Collector 新增 `rpc_timeout_seconds`，預設每個查詢最多 120 秒；只接受大於零、有限且不超過 600 秒的數字。錯誤參數在建立輸出或呼叫工具前拒絕。這是逐次查詢的執行期限，不能增加目標、模型或使用者的既有預算。

新紀錄使用 schema `2.0.0` 並保存期限；舊 `1.0.0` 的原始紀錄仍可查核。不允許舊版本混入新欄位，也不允許新版本省略期限。重新計算 hash 不能讓錯誤紀錄變成合格。

較長的等待時間仍可能失敗。逾時、未完成分頁或載入錯誤仍是 `partial`，不能假裝取得零個插件，也不能據此宣告隔離、研究品質或正式 A/B 通過。producer05 的原始失敗保留，不改寫。

## 大型回覆與錯誤原因

登入後的 producer08 在開始模型之前停止：`plugin/list` 回覆超過舊有 4 MiB 上限，卻被誤報成 JSON 錯誤。新收集器直接以有限長度讀取 bytes，單一 JSON 回覆上限 64 MiB，整次 RPC 原始輸出上限 128 MiB。這些是私有紀錄的安全界限，不是研究投入預算，也不把大型工具清單塞進模型 context。

大小超限、UTF-8 錯誤、JSON 格式錯誤、讀取器故障及 RPC 逾時分開記錄；超限時只保存有限的診斷與實際讀取長度，不把截斷内容當成完整工具清單。4 MiB 以上的合法回覆能保存及查核，不改變搜尋、插件、MCP、權限或模型設定。真實登入環境是否成功，仍需以修復後的新紀錄驗證。

即使最後一筆預期回覆已收到，後面才出現的讀取錯誤仍會保存，收集結果必須失敗。正常回覆不能遮住後續故障；有限的錯誤原因只記一次。

## 唯讀的呼叫紀錄查核

`producer_replay.verify_producer_inventory` 接受凍結的 capture request、telemetry root 與外部保存的 producer receipt。它重用既有原始檔、runtime、來源版本及 trace 驗證，不依賴目前環境變數，不呼叫模型／API、不改寫紀錄，也不宣告 formal-ready。Synthetic archive 不能進入這個公開接口。

回傳資料分開列出工具清單狀態、實際嘗試的模型／工具／子 agent 數、呼叫紀錄是否完整，以及 tokens 是否完整。已取消的呼叫仍是一次嘗試；沒有回報的 tokens 和費用保留 `null`。呼叫次數完整不能證明 token 預算合格，工具清單 `partial` 也不能被完整的呼叫次數抵銷。這是保留原執行環境的嚴格 replay，不能當成跨機器或 provider 的執行證明。

兩個研究預演、每個角色的隔離、rubric 校準及正式 A/B 仍是另外的門檻。一般使用者只跑 B；這些查核幫助他們看懂結果的依據，不要求每位使用者執行 A/B。
