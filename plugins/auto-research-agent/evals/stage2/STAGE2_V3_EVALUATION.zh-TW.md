# Stage 2 v3：研究流程、平衡評分與透明交付

交付物可以選擇保存「已登記的內容歷史」：候選修訂、比較表更新和補查
沿著原本的事件及來源版本保留，搬到其他電腦仍能重新核對。這個 v2
紀錄只證明內容曾變更並登記，不證明作者、模型呼叫成功或使用者同意。
不能把主模型整理的文件冒充為另一個 agent 已執行的研究。

實際獨立查核、外部評語、人工覆核及正式 A/B 仍各自保存證據。
只改表格而未修改候選，不新增候選修訂；未知及待覆核狀態照樣保留。

Stage 2 幫使用者從文獻走到可以選擇的研究方向。一般使用者只跑
Codex＋研究 harness，不需要自行跑 A/B。A/B 是開發團隊另外做的比較實驗。

## 研究怎麼走

確認過的需求與 Stage 1 證據 → 比較 → 開放發想 → 初篩 → 獨立挑戰與
可行性查核 → 有目的補查 → 新來源快照及影響清單 → 修正與重新查核 →
proposal 與外部評分 → 使用者選擇 → Stage 3。

兩條發想入口平等：改善既有設計，或提出有依據的新概念。
不要求固定候選數、假設實驗或複雜方法。探索、理論、重複及驗證研究
也能使用。沒有值得推薦的方向可以交付零推薦，仍須說明原因與下一步。

Stage 1 的 exploratory acceptance 只允許明確啟動 Stage 2 探索；
來源的 review-only、continue、unknown 與證據層級完整保留。它不能
把資料不足變成科學證據已充分，也不能代替使用者同意執行 Stage 3。

## 內部 checker 與外部評分不同

內部五面向是：機會成立、潛在價值、可回答性、材料可行性、執行可行性。
它幫研究流程決定推薦、修正、暫存或淘汰。外部 judge 評的是判斷品質：
我們有沒有比較對、定位對、改對，並給使用者有用且誠實的選擇包。
查出方向不可行並正確處置，可以得到高品質分數。

| 面向 | 三個子項 | 白話問題 |
|---|---|---|
| P4 | 忠實呈現、可比條件、綜合推論 | 前人有沒有講對、能不能比、比完學到什麼？ |
| P5 | 前例定位、貢獻與邊界、依證據修正 | 前人做到哪裡、我們多了什麼、發現問題有沒有真的改？ |
| P6 | 研究價值、可行性、處置與選擇包 | 為何值得、材料與資源是否適合、使用者能否據此選擇？ |

每项 0＝已觀察錯誤或缺失，1＝部分充分，2＝充分有據。
需要的查核證據不可得是 null，不是 0；評估器逾時或解析故障另記。
每面向三項合計／6×100。任一必要項目 null，完整面向也為 null。

原生模型無法執行、容量不足或中斷，是執行失敗，不是研究方向得 0 分。
Controller 先確認原生呼叫完成，才進入成功紀錄查核及擷取；缺少完成
狀態也會停止。原始失敗紀錄保留，缺席 reviewer 不算同意，不自動重試，
也不能把這次呼叫算成完整預演或正式 A/B。
不縮分母、不把三面向相加。同一問題只有導致不同的具體缺失，才分別扣分。
完整 anchors 在 [v3 rubric](../rubrics/stage2-general.v3.json)，
精確定義在 [操作型定義](../OPERATIONAL_DEFINITIONS.zh-TW.md)。

例如，宣稱月資料可用但沒有月變數是可行性判斷錯誤；
查到缺變數並暫存方向，可以得 2。只改寫研究問題但未重查受影響的
可回答性與材料，修正品質最多是 1。新方法效果未知本身可以是研究問題。

## 每份選擇包如何評

1. 凍結評分前的核心 selection、來源版本、rubric、judge 設定及程式 bytes。
2. R1、R2 用獨立 context，先看科學內容、存初評，再看實際處置；
   不看對方分數或內部 PASS。來源中的指令只當資料。
3. 分數、狀態或重大錯誤不同時交 ADJ；保留三者原始評語。
4. 低信心、重大錯誤、必要來源不可取得、分歧等既定 trigger 需要具名覆核。
   未完成覆核顯示待覆核，不假造 Eric 簽名，不宣稱正式改善。
5. 產生同一份資料的 Markdown、HTML、wiki 投影及檔案 manifest。

評估失敗仍可交付可讀的研究 proposal，但要清楚標示未完成評分。
只有科學內容變更才需要重評；改版面不改核心 selection，不需重呼叫 judge。
可恢復單元必須與外部保存的 receipt、來源、設定及原始呼叫一致。

日常 CLI 與透明交付已實作，隨 delivery PR 提供；正式安裝請使用核心組合併後的版本。
工程測試通過不等於兩個完整研究預演或正式 A/B 已完成。
具名覆核到達後，使用 `stage2_live finalize-daily-v3` 並提供外部保存的 parent replay receipt 建立另一份結果，
綁定原 bundle 與 audit 的 hash；不覆寫原結果，也不重呼叫 judge。
若 R2 失敗，R1 已完成的九項評語仍保留，完整面向分數保持 null。

## 日常執行預檢與失敗恢復

每個實際使用的 profile／workspace 都須有相符的原生呼叫證據。
日常 production probe v1.1 可保留相對的 `source_path` 作為封包索引，
同時使用絕對的 `command_path` 讀取檔案。兩者必須指向已固定 workspace 的同一檔案；
nonce、shell bytes、原生工具結果、來源範圍和路徑別名防護仍全部檢查。
舊 v1.0 保留，正式隔離 probe 不使用這個日常 v1.1 契約。
原生讀、寫、搜尋與子 agent 成功，只能證明這些能力；完整 inventory 及檔案隔離
尚未查核時仍明示 unknown。不能用日常 PASS 宣告 formal-ready。

待解分歧識別字未對齊時，會列出 required／missing／extra 的主張識別字。
這幫助擷取器知道漏了哪個判斷，不允許只複製識別字就通過：來源、候選版本、
獨立初評及實質解決理由仍須核對。保留失敗原文與 attempt；只在相關輸入或程式
已有核實修正時依凍結政策恢復，不重跑已完成的研究或查核。

比較表也要分清楚格子的種類。「用了什麼方法」填文字，「樣本有幾個」填數字，
「有沒有某個功能」才用有／無。功能格的解釋另放理由欄；不知道就保留 unknown
與空值，不能改成「沒有」。格式錯誤指出研究、版本與比較面向，讓有限的一次
修正知道要改哪格。系統保留失敗稿，不自動改值或放寬來源查核；
格式修好只代表紀錄可使用，不代表研究更好或方向已可行。

## 使用者會拿到什麼

概要先呈現方向、推薦理由、資源、限制與 P4–P6 評估狀態。
新版 HTML 在方向概要後顯示獨立評分概覽，提供跳到完整九項評語的連結；
具名覆核待完成時，分數標為 provisional，未知仍顯示 Unknown。
交付 manifest 的 `presentation_version` 區分新舊排版；舊版封包仍可依原版面重建，
改版面不改核心 selection 或 rubric，也不重跑 judge。
九項評語區可展開 R1／R2／ADJ 的分數、理由、信心、未知及覆核狀態；
證據連結帶到原文位置與版本。候選資料、模型、工具包含網址／版本、
存取與授權、成本依據、限制與替代方案。取得失敗、零結果、未知和
核對可用分開顯示，不把能下載視為足以回答研究問題。

核心 selection 先 hash，再評分，最後 HTML 引用 bundle；
manifest 核對輸出，避免讓 HTML 與 bundle 互相 hash。
原始評語不會被最終分數覆蓋。來源文字轉義，不把私有原文或憑證放進公開 Git。
選擇包已準備與使用者已選定方向分開記錄。

## 補查後的修訂如何接到評分

新來源帶來候選修訂時，必須保留原始 `Stage2SourceUpdate`、前後來源快照、
影響原因及新增的證據 ID。交付 CLI 的 `--source-update-receipt PATH SHA256`
可重複提供這些原始紀錄；SHA256 必須是呼叫端保存的原檔 hash。
程式核對相鄰快照、候選版本與來源後，才建立可攜的修訂依據與評分用 action record。
原 checker 封包及其缺失標示不改寫，不補造過去沒有發生的 checker event。
新交付 manifest 為 v1.1；未使用此接口的 v1.0 仍依原規則處理。

這些紀錄證明「為何修訂、改了什麼」，不能單獨證明原生 agent 已執行、
科學內容正確或使用者已同意。缺少其他必要處置紀錄時，外部評分仍保持未完成。
只有與當前候選及來源相符的完整紀錄，才允許進入独立 judge 評分。

## 使用原有來源修正內容

有時不用找新文章，就能查出比較或候選方向的錯誤。例如，同一本書的
下一頁已經解釋研究對象，原先只讀到背景。此時應保存修訂與依據。

`Stage2ContentRevision` 支援原有來源上的修訂，保留來源身分、版本及
原始 bytes。既有 evidence 與候選歷史不能改寫；可補充同一來源的
逐字節錄及 `lines N-M` 位置。新增節錄必須核對原文，不需要新增 source。
沒有新增 evidence 的純內容修訂也合法。

操作順序如下：

1. `stage2_live prepare-content-revision-input` 接收原 packet、來源根目錄
   及新增節錄清單；沒有新增節錄時使用空清單。
2. 保存修訂原稿，使用 `stage2_live extract` 的
   `--update-mode replace-comparison-unresolved` 擷取新版。
   預設 append 模式仍供原先生成流程使用。
3. 以既有 snapshot／revision 接口建立不可變的新快照及影響理由。
   修訂後的目前比較與 unresolved 取代舊 current view，歷史仍保留。
   Exploratory 匯入時接受的原始限制仍須逐字保留，不能因更新未解事項
   而消失。已被修正的暫時問題可以更新；原始接受範圍、來源層級及
   acceptance 綁定不因此改變。保留限制本身也不算完成科學修訂。
4. `stage2_live content-revision` 驗證父子 packet、相鄰快照、原稿、
   擷取呼叫的外部 receipt 及受影響候選，產生修訂依據。
5. 對受影響的新版候選重新獨立查核，再交付與外部評分。舊版通過不算。
   交付既有 `--source-update-receipt PATH SHA256` 接口也接受此種
   已驗證的內容修訂 receipt；兩種 kind 仍分別核對，不能互相冒充。

真正的內容改變才算修訂。只增加版本號、只改處置標籤或重算 hash，
不能證明完成修正。來源 bytes、原始證據、producer receipt 或新版查核
不符時拒絕接受；此紀錄本身不能宣稱內容正確或研究品質改善。

評分者也會誤讀背景或漏掉上下文。若原文查證推翻評語，應保留原評語，
另記 evaluator error、補齊有位置的原文，再獨立重評。
節錄未出現的資訊，須區分全文已有但未納入、原文不可取得及實際不存在；
不能直接當成造假。三位評分者同意，也不能代替原文。

## 如何驗收

資源的 `available/restricted/unavailable` 必須有非 metadata 證據及 UTC
查核時間；缺少依據時保留 `unknown` 與空時間。來源取得時間只支持當時
有記錄的來源查核，不能冒充現在的資料存取、授權或整個方向已可行。
複合資源不能用一個已知項目替所有項目背書。

工程測試核對來源／版本／hash、九項完整性、null 分母、舊版相容、
修訂後判斷失效、缺席 reviewer、恢復與過期選擇，以及三種投影的一致性。
它證明程式行為，不證明 AI 能自行找出研究問題。

新版 judge 校準使用獨立的新案例：九項各 0／1／2／unknown，36 anchors；
每項一個代表案例各四種等義變體，再 36 份。共 72 份、144 個指定判斷。
整體與每項符合參考範圍 ≥90%，R1／R2 一致 ≥85%，變體一致 ≥90%；
明確事實與重大錯誤不得誤判，重大分歧均需釐清。模型呼叫數另計。
不能用大量無關 null 提高正確率，不能刪掉失敗案例縮分母。

校準 prompt 和 schema 的案例／證據 ID 都先換成不透露答案的代號。
目標分數、變體類型、參考答案及對照表留在評估端，模型結果通過查核
後才還原 ID。2026-10-03 的新盲化案例共 18 次真實模型呼叫，
144／144 判斷符合參考範圍，每項符合率、一致率與變體一致率為 100%。
原先使用含分數 ID 的校準保留為受污染診斷，不能用來驗收。
上述數字只適用本批控制案例，不是研究品質改善或跨題目泛化的證明。
去識別結果及證據 hash 見
[校準紀錄](../evidence/stage2-v3-blind-calibration-2026-10-03.json)。

美國老化與 flaky-test 兩個真實 B 預演另查完整流程、補查、修訂、
外部評分與可讀交付。純理論另做離線檢查；故障注入不能冒充研究發現。

正式三對 A/B 還需要物理隔離、完整用量、校準、兩預演及投入政策凍結。
A 保留相同原生能力。P5、P6 各至少兩對改善且零退步，P4 零退步，
B 無新增重大錯誤；必要證據或覆核不足為 inconclusive。
校準通過、日常 context 分開或流程跑通，都不等於這些門檻已通過。

本版本保留 v2 與 QA03，尚不改寫歷史結果。PR 的改善聲明在正式結果前為
**not yet demonstrated**，核心組審查與 merge 僅在 WenyuChiou fork。

## 查核者也必須看到方向的資源條件

新的 initial review view v1.1 將目前候選版本的資源表一起交給獨立查核者。
它保留必要／備案、存取、授權、成本依據及 unknown；不傳其他方向的資源，
也不傳另一位查核者的結論。原生 controller 使用這個新版；舊 v1.0 紀錄
仍依原 bytes 與 hash 驗證，不能偷偷換成新版。

例如，備案資料不能交給 LLM，不代表主方案已經不可行。要先看它是否必要，
以及主方案的實際條件。必要資料或 API 預算還沒查明時，不能宣稱可做；
也不能只因未知就說已證明做不到。證據不足用 unknown/null；有部分支持
可以依既有規則評 1；有證據顯示必要條件不成立才評 0。

五面向的查核規則會同時出現在研究提示與無工具擷取提示中。擷取器仍保存
原始判斷，不能把明確的錯誤分數自動修成較好的分數。若新原文或完整條件
推翻評語，保留舊稿並以新版本重新查核。缺少 reviewer、版本不符或混用
新舊查核輸入都不能算成同意。

這修正的是查核輸入與判斷規則傳遞，不改九項外部 rubric。測試通過只證明
資源和規則有送到、錯配會被拒絕；實際判斷仍須查核，完整預演與正式 A/B
另行驗收。內容驗收之前，Wiki 只能明示為草稿，不能假裝已完成研究選擇包。
