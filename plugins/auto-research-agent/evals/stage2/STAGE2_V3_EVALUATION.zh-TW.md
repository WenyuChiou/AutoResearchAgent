# Stage 2 v3：研究流程、平衡評分與透明交付

Stage 2 幫使用者從文獻走到可以選擇的研究方向。一般使用者只跑
Codex＋研究 harness，不需要自行跑 A/B。A/B 是開發團隊另外做的比較實驗。

## 研究怎麼走

確認過的需求與 Stage 1 證據 → 比較 → 開放發想 → 初篩 → 獨立挑戰與
可行性查核 → 有目的補查 → 新來源快照及影響清單 → 修正與重新查核 →
proposal 與外部評分 → 使用者選擇 → Stage 3。

兩條發想入口平等：改善既有設計，或提出有依據的新概念。
不要求固定候選數、假設實驗或複雜方法。探索、理論、重複及驗證研究
也能使用。沒有值得推薦的方向可以交付零推薦，仍須說明原因與下一步。

Stage 1 的 exploratory acceptance 只允許明確啟動 Stage 2 探索；
來源的 review-only、continue、unknown 與證據層級完整保留。它不能
把資料不足變成科學證據已充分，也不能代替使用者同意執行 Stage 3。

## 內部 checker 與外部評分不同

內部五面向是：機會成立、潛在價值、可回答性、材料可行性、執行可行性。
它幫研究流程決定推薦、修正、暫存或淘汰。外部 judge 評的是判斷品質：
我們有沒有比較對、定位對、改對，並給使用者有用且誠實的選擇包。
查出方向不可行並正確處置，可以得到高品質分數。

| 面向 | 三個子項 | 白話問題 |
|---|---|---|
| P4 | 忠實呈現、可比條件、綜合推論 | 前人有沒有講對、能不能比、比完學到什麼？ |
| P5 | 前例定位、貢獻與邊界、依證據修正 | 前人做到哪裡、我們多了什麼、發現問題有沒有真的改？ |
| P6 | 研究價值、可行性、處置與選擇包 | 為何值得、材料與資源是否適合、使用者能否據此選擇？ |

每项 0＝已觀察錯誤或缺失，1＝部分充分，2＝充分有據。
需要的查核證據不可得是 null，不是 0；評估器逾時或解析故障另記。
每面向三項合計／6×100。任一必要項目 null，完整面向也為 null。
不縮分母、不把三面向相加。同一問題只有導致不同的具體缺失，才分別扣分。
完整 anchors 在 [v3 rubric](../rubrics/stage2-general.v3.json)，
精確定義在 [操作型定義](../OPERATIONAL_DEFINITIONS.zh-TW.md)。

例如，宣稱月資料可用但沒有月變數是可行性判斷錯誤；
查到缺變數並暫存方向，可以得 2。只改寫研究問題但未重查受影響的
可回答性與材料，修正品質最多是 1。新方法效果未知本身可以是研究問題。

## 每份選擇包如何評

1. 凍結評分前的核心 selection、來源版本、rubric、judge 設定及程式 bytes。
2. R1、R2 用獨立 context，先看科學內容、存初評，再看實際處置；
   不看對方分數或內部 PASS。來源中的指令只當資料。
3. 分數、狀態或重大錯誤不同時交 ADJ；保留三者原始評語。
4. 低信心、重大錯誤、必要來源不可取得、分歧等既定 trigger 需要具名覆核。
   未完成覆核顯示待覆核，不假造 Eric 簽名，不宣稱正式改善。
5. 產生同一份資料的 Markdown、HTML、wiki 投影及檔案 manifest。

評估失敗仍可交付可讀的研究 proposal，但要清楚標示未完成評分。
只有科學內容變更才需要重評；改版面不改核心 selection，不需重呼叫 judge。
可恢復單元必須與外部保存的 receipt、來源、設定及原始呼叫一致。

下述日常 CLI 與透明交付功能須待後續 delivery PR 合併後才可使用；本 PR 是評分契約。
具名覆核到達後，使用 `stage2_live finalize-daily-v3` 並提供外部保存的 parent replay receipt 建立另一份結果，
綁定原 bundle 與 audit 的 hash；不覆寫原結果，也不重呼叫 judge。
若 R2 失敗，R1 已完成的九項評語仍保留，完整面向分數保持 null。

## 使用者會拿到什麼

概要先呈現方向、推薦理由、資源、限制與 P4–P6 評估狀態。
九項評語區可展開 R1／R2／ADJ 的分數、理由、信心、未知及覆核狀態；
證據連結帶到原文位置與版本。候選資料、模型、工具包含網址／版本、
存取與授權、成本依據、限制與替代方案。取得失敗、零結果、未知和
核對可用分開顯示，不把能下載視為足以回答研究問題。

核心 selection 先 hash，再評分，最後 HTML 引用 bundle；
manifest 核對輸出，避免讓 HTML 與 bundle 互相 hash。
原始評語不會被最終分數覆蓋。來源文字轉義，不把私有原文或憑證放進公開 Git。
選擇包已準備與使用者已選定方向分開記錄。

## 如何驗收

工程測試核對來源／版本／hash、九項完整性、null 分母、舊版相容、
修訂後判斷失效、缺席 reviewer、恢復與過期選擇，以及三種投影的一致性。
它證明程式行為，不證明 AI 能自行找出研究問題。

新版 judge 校準使用獨立的新案例：九項各 0／1／2／unknown，36 anchors；
每項一個代表案例各四種等義變體，再 36 份。共 72 份、144 個指定判斷。
整體與每項符合參考範圍 ≥90%，R1／R2 一致 ≥85%，變體一致 ≥90%；
明確事實與重大錯誤不得誤判，重大分歧均需釐清。模型呼叫數另計。
不能用大量無關 null 提高正確率，不能刪掉失敗案例縮分母。

校準 prompt 和 schema 的案例／證據 ID 都先換成不透露答案的代號。
目標分數、變體類型、參考答案及對照表留在評估端，模型結果通過查核
後才還原 ID。2026-10-03 的新盲化案例共 18 次真實模型呼叫，
144／144 判斷符合參考範圍，每項符合率、一致率與變體一致率為 100%。
原先使用含分數 ID 的校準保留為受污染診斷，不能用來驗收。
上述數字只適用本批控制案例，不是研究品質改善或跨題目泛化的證明。
去識別結果及證據 hash 見
[校準紀錄](../evidence/stage2-v3-blind-calibration-2026-10-03.json)。

美國老化與 flaky-test 兩個真實 B 預演另查完整流程、補查、修訂、
外部評分與可讀交付。純理論另做離線檢查；故障注入不能冒充研究發現。

正式三對 A/B 還需要物理隔離、完整用量、校準、兩預演及投入政策凍結。
A 保留相同原生能力。P5、P6 各至少兩對改善且零退步，P4 零退步，
B 無新增重大錯誤；必要證據或覆核不足為 inconclusive。
校準通過、日常 context 分開或流程跑通，都不等於這些門檻已通過。

本版本保留 v2 與 QA03，尚不改寫歷史結果。PR 的改善聲明在正式結果前為
**not yet demonstrated**，核心組審查與 merge 僅在 WenyuChiou fork。
