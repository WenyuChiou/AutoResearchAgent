# Stage 2：先確認「正在判斷什麼」

這份診斷不改 P4–P6，也不提供唯一正確研究方向。它檢查評估器是否看懂候選、主張與初篩決定的差別。

## 三個不同的對象

| 對象 | 例子 | 否定它代表什麼 |
| --- | --- | --- |
| 研究候選 | 用簡單規則修正時間對齊 | 不繼續投入這個方向，或先修改 |
| 主張 | 前人從沒做過這個方法 | 撤回首次提出的說法；方向可能仍值得驗證 |
| 初篩決定 | 因為方法太簡單，所以淘汰 | 撤回不合理的淘汰理由；重新查核方向 |

每筆判斷保存 `disposition_target`、理由、來源及下一步。五個面向仍然評研究候選：機會成立、潛在價值、可回答性、材料可行性、執行可行性。潛在價值不是已證明的效果大小。新方法能不能成功可以是研究問題；資料是否存在或能否驗證，不能靠猜。

## 資料和執行

`diagnostics/cases.v2.json` 保存 13 組供給事實的控制情境；`variants.v2.json` 定義原始、順序、篇幅、聲望、偏好措辭五種呈現。合計 65 份案例輸出，通常由五次主要模型呼叫產生。修正或傳輸重試另外計數，不能把 65 稱為 65 次獨立實驗。

舊版情境及失敗不覆寫，對照見 `diagnostics/LEGACY_MAPPING.zh-TW.md`。先用 `stage2_eval prepare-diagnostics` 綁定來源和呈現方式，再將各單元交給 `stage2_live calibrate`。模型、推理、政策和保存位置均由呼叫者明確提供。沒有將研究題目改為這些控制情境。

新傳輸版本 `source-id-v1` 讓模型只選 `evidence_id`。程式依該案例的原文、作品和版本還原文字；錯案例、錯來源、被改動的 hash 或自填引文都拒絕。舊 `verbatim-v1` 結果繼續可讀，但不會被悄悄改成新版成功結果。

## 如何判斷校準有沒有通過

1. 程式核對案例、來源、對象、分數及完整度。未知必須是 null，不能寫成 0。
2. 獨立查核者先讀事實並保存初評，再看模型的判斷。
3. 比較「對象＋理由＋證據＋下一步」，不能只比 reject 或 recommend 字串。
4. 列出重大錯誤、誤報、未解問題，以及呈現變化造成的判斷差異。正向情境必須能保留值得研究的簡單方法和新概念。
5. 程式或擷取故障列為 evaluator failure。輸出通過 schema 不等於科學判斷正確。

模型呼叫沿用 600 秒、一次暫時性傳輸重試、每單元最多一次語意修正的既有政策。修正仍失敗時保留失敗；只有相關程式或輸入已改正後，才建立新版本診斷，說明原因。實際成本沒有回報時寫 unknown。

校準通過仍不代表 harness 改善。正式 A/B 另需有效隔離、完整預演、凍結計畫及獨立評分。Eric 只在既定人工覆核條件出現時提供真實覆核；程式不代簽，也不把每次控制情境都變成人工必填表。

## 執行與變體綁定

### 「不成立」和「還不知道」分開

診斷輸出新增可選的 `2.1.0`；舊 `2.0.0` 提示、結果與檔案不覆寫，預設仍為舊版。
在 `prepare-diagnostics` 加 `--output-version 2.1.0` 才會建立新版單元。
新版每個面向保存 `judgment_basis` 及 `negative_evidence_ids`：

- **0 分**：有來源顯示必要條件不相容，例如資料字典明確沒有必要變數。必須引用該面向的負向證據。
- **unknown／null**：尚未查到變數或未確認取得條件，說清楚下一步要查什麼。沒有找到，不等於不存在。
- **1／2 分**：分別表示部分或充分支持；不能夾帶 0 分用的負向證據 ID。

程式只確認版本、來源及 ID 綁定，不能靠欄位判定證據真的支持 0 分。
獨立查核者仍要讀原文；成功通過 validator 不代表科學判斷正確。
執行與唯讀重播均使用單元凍結的輸出版本，錯版本不能偷換成舊 schema。
這是診斷輸出的版本，與下方執行封存結果的 `2.2` 是不同接口。
舊 65 份輸出中那筆「尚未查清楚卻評 0」仍保留；新增程式測試不代表已重跑並完成語意校準。

執行入口只接受獨立原生 Codex 執行檔，拒絕可能另呼叫未綁定程式的 script／npm shim。每次執行與恢復均重查實際 bytes。

新單元保存完整 recipe，重新產生提示並比對 variant、順序、篇數與來源傳輸方式。旧 2.1 診斷不覆寫；只讀查核須另提供當時凍結的 recipe。新執行結果為 2.2，rubric 與來源事實不變。
