# Stage 2：如何閱讀提案、討論與確認方向

目前這部分通過的是程式與契約測試；是否真的提出更好的研究方向，仍須由獨立
評估及 A/B 判斷。不要把「報告檔案完整」說成「研究已證實可行」。

## 你會拿到什麼

先在對話中看選項比較、推薦理由、代價和待決問題，再開英文 Markdown 或 HTML
閱讀完整依據。兩份報告使用同一份查核資料，保留支持與反對證據、五面向判斷、
先前版本及未知。v2 封包已有的篇名、作者、年份、期刊／版本、DOI 或網址會在最終
報告中列出，並連回來源與 claim。文獻角色附理由；每個原文片段只顯示明確連到它的
角色，不把整篇的角色套到每句話。這些是已保存的判斷，並非重新證明經典地位或
科學結論。摘要仍是摘要。v1 或缺少的欄位會明示，不能把 source ID 當完整引用。

報告包會另存來源、獨立初評、綜合判斷和每個檔案的 hash。原始研究快照不改動。
這樣可以追查「當時看的是哪份資料」，但不能只靠 hash 證明 AI 說的科學結論正確。

## 四種容易混淆的狀態

| 狀態 | 白話意思 |
|---|---|
| 查核還沒齊 | 有 reviewer 沒回覆或失敗；不能當成同意 |
| 本地報告準備好 | 要求的查核與綜合紀錄齊了；仍要看原生執行與來源證據 |
| 有可推薦選項 | 這個版本通過內部五面向檢查；其他暫存選項不會直接拖垮它 |
| 使用者已選擇 | 保存本人原話，綁定看過的報告與候選版本；不等於已授權跑實驗 |

零推薦也是合法結果，只要說明原因和下一步。尚待修訂的版本不能被選成已查核版本。

## 問答與修改

你可以要求比較、解釋、縮減、合併或重啟方向。只有真正缺少的重要條件或取捨，
才需要問你；其餘已授權工作繼續執行。系統不能把「請再解釋」記成「我同意」。

保存原生對話中的 user 訊息與完整原話；assistant 或工具的文字不能替代你的選擇。
如果澄清、查核或資料發生變動，要產生新報告，再確認新版本。重送同一個已完成
決定可以核對後重用，不會再增加一次決策事件。

若要改 Markdown，先改一份草稿。保存草稿和你的修改要求，轉成新版候選並重查，
不要改掉已發布的報告後重算 hash 冒充舊版。程式會保存修改要求，但不會自行
理解任意 Markdown 修改對科學判斷的影響；這由研究 agent 依來源重新處理。

## 交給 Stage 3

可以選一個或多個方向。交接包含方向版本、來源、查核、資源、限制、未解事項和
什麼證據會讓我們改變選擇。Stage 3 才做詳細方法、資料處理、比較組、分析、驗證
和排程；多方向要算總成本。若發現必要條件不成立，帶證據回到 Stage 2。

操作命令與欄位見 [交付接口](../../references/stage2-delivery.md)。所有個人身分與
授權仍由原生 host 確認；本地 JSON 和角色欄位不能自己製造真人簽核。
