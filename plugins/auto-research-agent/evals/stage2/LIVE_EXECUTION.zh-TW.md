# Stage 2：真正執行與評估的操作邊界

目前加入 `stage2_live`，讓原生 Codex 做研究，再保存可查核紀錄。
它仍是 experimental；工具能跑，和研究品質變好，是兩件要分別驗證的事。

## 一次研究怎麼走

1. 讀已確認的需求、資源限制與 Stage 1 證據，產生研究任務。
2. 原生 agent 使用搜尋、閱讀及子 agent 能力，先寫自然語言提案。
3. 不使用工具的擷取步驟，把提案轉成比較與候選紀錄。模型選片段編號，
   程式還原原文；不要求模型猜字元位置。擷取失敗時保留原提案。
4. 挑戰者和可行性查核者各自閱讀證據、先保存初評，再進行必要的綜合。
   查核內容仍是機會、價值、可回答性、材料及執行五個面向。
5. 新來源或新候選成為新的 snapshot；舊版通過不能冒充新版已查核。
6. 以相同紀錄產生報告，在聊天中說明選項，由使用者選擇。使用者還沒
   選擇時，不能寫成已同意，也不能自動開始 Stage 3 實驗。

完整命令介面與信任邊界見 [native call 說明](../../references/stage2-live.md)。
每個動作的輸入、原始結果及 receipt，應接入既有 workflow 的 action record。
這些命令不會自行建立另一套排程器，也不會替使用者偷偷增加研究預算。

## 檢查研究方向，和評估 harness，分開做

Production checker 協助研究：指出問題、補查、修改、暫存或推薦。
外部 R1／R2 evaluator 則評 P4–P6：比較是否合理、方向是否有據、選擇包
是否有用。兩者不能共用評分結果，不能把內部 PASS 當作 A/B 進步。

R1／R2 先各看內容，再看處置。分數或重大錯誤不一致才請 ADJ。
需要 Eric 覆核時保留 `audit-required`，不能由 AI 代簽。
評估器失敗是評估失敗，不能把受測 agent 計成零分。

## 我們怎麼知道紀錄可信

- 原始 prompt、來源、程式、執行設定與輸出都綁定 hash。
- 另外保存 receipt，才能發現有人連紀錄和自填 hash 一起改掉。
- 擷取與評分也會回傳 `replay_receipt`。用 `--replay-receipt-output` 另外保存，
  恢復時以 `--replay-receipt` 提供；不能事後從待查封包自行重建可信收據。
- 使用 Codex 原生執行檔；不接受只綁定 npm、JavaScript 或 shell 啟動腳本。
- 完成的呼叫恢復前先重驗；內容或版本變了就不能冒充原本那次。
- 原生 session 日誌存在時一併保存；缺少時明示，不能宣稱完整可追溯。
- 個別 CODEX_HOME 不等於安全隔離；執行端仍需檢查實際掛載與工具設定。
- 模擬測試清楚標 synthetic，不會拿來宣稱真實呼叫或科學品質改善。

正式三組 A/B 仍須等完整預演、診斷、校準及投入政策凍結。P5／P6 各至少
兩對改善且零退步，P4 零退步，B 不新增重大錯誤；證據不足就報 inconclusive。
